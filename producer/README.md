# producer/

A minimal Node + TypeScript playground for talking to the local Kafka broker. Despite the folder name, it contains both a producer and a consumer.

Everything here is deliberately small. The goal is to observe Kafka's behaviour, not to build features.

## Contents

| Path              | Purpose                                                                                                                                            |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/producer.ts` | Connects to Kafka, sends one message (key `125`) to the `orders` topic, logs the result, disconnects                                               |
| `src/consumer.ts` | Joins consumer group `notification-service`, subscribes to `orders` with `fromBeginning: true`, logs every message (partition, offset, key, value) |
| `package.json`    | Dependencies and settings. `"type": "module"` makes the project ESM                                                                                |
| `tsconfig.json`   | TypeScript config generated by `tsc --init` (`module: nodenext`)                                                                                   |

## Dependencies

- `kafkajs`: the Kafka client library
- `typescript`, `tsx`, `@types/node` (dev): `tsx` runs `.ts` files directly with no build step

## Prerequisites

The broker must be running and the `orders` topic must exist (1 partition). From the repo root:

```bash
docker compose up -d
```

Then create `orders` in Kafka UI at http://localhost:8080.

## Running

```bash
npm install

npx tsx src/consumer.ts   # long-running, stop with Ctrl+C
npx tsx src/producer.ts   # sends one message and exits
```

## Things worth knowing

- **Broker address.** Both files connect to `localhost:9092`, the `HOST` listener. This is correct because the apps run on the host machine. An app running inside the Compose network would use `kafka:19092` instead.
- **Offsets are assigned by the broker.** The producer's send result includes the partition and the offset the broker chose.
- **`fromBeginning` only matters for a new group.** Once `notification-service` has a committed offset, restarting the consumer resumes from that offset instead of replaying the topic.
- **Offset commits are automatic.** KafkaJS commits as messages are processed by default. Controlling this explicitly is a Phase 3 topic.
- **Running the producer twice appends twice.** Kafka does not deduplicate by key.

## Known warnings

- `KafkaJS v2.0.0 switched default partitioner`: harmless here. It will matter when topics have multiple partitions, because it decides which key goes to which partition.
- `TimeoutNegativeWarning`: a Node warning that does not stop messages being sent. Root cause not yet investigated.
